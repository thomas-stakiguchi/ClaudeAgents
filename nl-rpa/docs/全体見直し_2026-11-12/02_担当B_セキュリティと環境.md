## (3) 食い違い・欠陥の一覧

高（安全：誤実行・迂回・漏えい）に当たるものは、確認した範囲では見つかりませんでした。以下は、中・低です。

### 中

**F1（中）SEC-6：接続先がビルド時の定数でなく、実行時の設定（環境変数）で変わる**
- 何が：仕様は「接続先はビルド時の定数で固定。実行時の設定では変えられない。定数にないホストは許可リストにも追加できない」。実装の定数（`DestinationLimits::NAMES`、DestinationLimits.php:15）は、接続先の「名前」`stub` だけです。Chromeが通信してよい宛先は `Engine::stubOrigin()`（Engine.php:192-201）が、`NL_RPA_STUB_PORT` から `http://localhost:<ポート>` として作ります。アプリ自身のポート以外なら、1〜65535 のどれでも通ります。
- 再現：`NL_RPA_DATA_DIR=<tmp> NL_RPA_BROWSER=chrome NL_RPA_STUB_PORT=5432 NL_RPA_CHROME=/bin/true php -r '…app(Engine::class)->environmentName() / newBrowser()…'`。実測で `chrome@http://localhost:5432` になり、`ChromeBrowser` が作れました（Chromeは起動していません）。
- 直し方の案：許可するホストとポートの範囲を、`src/Policy` の定数（例：スタブの許可ポートの一覧）に置き、設定値がその中にないときは、起動時に拒否する。あわせて、そのテストを足す。TECH_STACK.md:128 の「制約」と同じ指摘なので、記載は正直ですが、仕様の要件とは別に残っています。

**F2（中）SEC-2：記録の検証 `Ledger::verify()` が、本番のコードから一度も呼ばれない**
- 何が：チェーンは作られますが、`verify()` を呼ぶのは tests だけです（grep）。実行前（Guard）にも、起動時にも、画面にも、検証がありません。README.md:11 と Ledger.php:124-126 は「部分的な改ざんのみ検知できる」と書いていますが、検知を行う場所がありません。
- 再現：`grep -rn "verify()" src app`（0件）。
- 直し方の案：ワーカーの開始時と、12-1の関数の前に `verify()` を呼び、失敗なら停止する。難しければ、README の表現を「検知する仕組みはあるが、まだ使っていない」に直す。

**F3（中）SEC-11d／12-1：ブラウザ部品の public メソッドが、Guard と個別登録を通らずに操作できる**
- 何が：仕様は「接続先ごとの部品は、この関数を通さずに操作できない作りにする」。`ChromeBrowser` の `typeText`／`clearText`／`openUrl`（ChromeBrowser.php:290,328 ほか）は public で、登録（自動保存なし等）も確認しません。付録A_確定:135 は「chrome-php 版では、ポートにも承認済みの登録を持たせて、登録外の対象を拒否する（1bまでに対応）」と約束していますが、`ChromeBrowser` は `OperationPolicy` を使っていません。
- 影響（推測）：今のコードでは、取り消し可否の判定は Runner だけにあり、計画からは迂回できません（取り消せない扱いの type_text／open_url は performIrreversible を通り、clear_text は「未対応」で止まる）。つまり、現状の悪用経路は確認できていませんが、設計上の穴です。
- 再現手順：なし（コードの読み取りによる）。
- 直し方の案：ポートの取り消せるメソッドの中で、`OperationPolicy` を使って「登録済みか」を照合し、未登録なら例外にする。「登録外の要素への typeText を直接呼ぶと拒否される」テストを足す。

**F4（中）3-3／SEC-7：AIの「根拠(source)」は、1文字でもシナリオに含まれれば「根拠あり」になる**
- 何が：`AiPlanGate::checkSources`（AiPlanGate.php:73-80）は、`source` がシナリオの部分文字列なら残します。長さの下限も、文単位の一致もありません。AIが補った取り消せない手順に、`"。"` のような1文字を `source` に入れると、承認画面の「AIが補った」の印と、「1つずつ確認しないと承認できない」の確認（PlanPresenter::aiSuppliedIrreversible）が働きません。
- 再現：実測。スタブの計画の S-003〜S-006 の source を `"ン"`／`"。"` に書き換えて `AiPlanGate::accept` に通したところ、エラーなしで受け入れられ、source はそのまま残りました。
- 影響：今のAIは固定のスタブなので、実害はありません。実AIをつなぐ前に直す必要があります。実行エンジン側の取り消し判定（OperationPolicy）には影響しません。
- 直し方の案：source が、シナリオの「文」（句点・改行で区切った単位）と完全に一致するか、一定の長さ以上の連続した一致を求める。満たさなければ null（AIが補った）。テストを足す。

**F5（中）LOC-8：限界の明記が、仕様の要求より薄い**
- 何が：LOC-8 は「この限界を、画面とREADMEに明記する」「1aと1bで書き分ける」。画面（layout.blade.php:17）は「記録の保護、専用のOSアカウントなどがあります」と一般的に触れるだけです。README は SEC-2 と SEC-10 を書いていますが、LOC-8 が挙げる SEC-6 の限界（実行エンジン・設定を実行者のアカウントから書き換えられる）は書いていません。README.md:5 は「いまは1a」と書く一方で、44-66行で本物のChromeを説明していて、1aと1bの書き分けになっていません。
- 直し方の案：画面に、3項目（SEC-2、SEC-6、SEC-10）を箇条書きで出す。README を、1aの項と1bの項に分ける。

**F6（中）9-2：ブラウザ部品を fake に戻すと、スタブのドライランが再び有効になる**
- 何が：仕様は「1bに入った時点で、1a（スタブ）のドライランは、すべて無効とする」。実装は環境名（stub／chrome@…）で区別するため、`NL_RPA_BROWSER=fake` に戻すと、古いスタブのドライランと最終承認が有効に戻ります。TECH_STACK.md:127 に「制約」として明記されています（開発の都合）。
- 直し方の案：1bに入ったら、`stub` の環境を許可する設定自体を無効にする（1bの設定では fake を選べないようにする）。または、ledger に「stub のドライランは無効」の記録を残す。

**F7（中）14-2：記録したバージョンの範囲で止まるのではなく、既定は「確認しない」**
- 何が：仕様は「docs/TECH_STACK.md に記録した範囲外のバージョンなら停止」。実装は `NL_RPA_CHROME_MAJOR` が空なら確認しません（config/nlrpa.php:27）。TECH_STACK.md に範囲の記録もありません（11-5）。
- 直し方の案：範囲を決めて TECH_STACK.md に書き、`chrome` モードのときは、範囲の設定を必須にする。
