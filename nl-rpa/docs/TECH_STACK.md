## 7. 通信遮断の事前検証の結果（2026-11-11。仕様14-6「1aの最初の作業」）

- 道具：`tools/verify-network/`（`php tools/verify-network/run.php`、`profile_and_debug.php`）。偽の外部サーバー（カナリア）に要求が届いたら、遮断の失敗とみなす
- 環境：Linux（クラウドの実行環境）、**PHP 8.3.6**（仕様の8.5.12ではない）、chrome-php/chrome 1.16.2、**Chrome for Testing 153.0.8010.12**。Windows・Macでは、未確認
- 対照（遮断なし）では、攻撃が外へ届くことを確認した（IP指定で15件すべて）。検査の道具は、機能している

### 7-1. 遷移の検査と、遷移以外の通信（15件の攻撃 × 外部をホスト名で指定／IPで指定）
| 方式 | 外へ届いた件数 | 届いたもの | 判定 |
|---|---|---|---|
| A：エンジンが、CDPの Fetch ドメインで、すべての要求を検査して、許可した接続先（スキーム・ホスト・ポートの完全一致）以外は失敗にする | 3〜4 / 15 | window.open、target=_blank、Service Worker、WebSocket（IP指定のとき） | **不合格**（単独では不十分） |
| A2：Aに、`--block-new-web-contents` を足す | 3〜4 / 15 | Aと同じ（フラグは、効かなかった） | **不合格** |
| B：Chromeの名前解決を、許可した名前以外は失敗にする（`--host-resolver-rules=MAP * ~NOTFOUND, EXCLUDE localhost`） | 0 / 15 | なし（IP指定の外部も、遮断された） | 合格（この15件で） |
| C：Chromeの通信を、使えないプロキシへ向け、許可した接続先だけ迂回する（`--proxy-server` と `--proxy-bypass-list=<-loopback>;localhost:ポート`） | 0 / 15 | なし | 合格（この15件で） |

- 15件：リダイレクト、window.open、target=_blank、iframe、meta refresh、JavaScriptによる遷移、fetch、XHR、WebSocket、sendBeacon、フォームの外部送信、ダウンロード、画像、スクリプト、Service Worker。許可した画面への遷移（基準）は、すべての方式で成功した
- Aが止めたもの：リダイレクト、iframe、meta refresh、JavaScriptによる遷移、fetch、XHR、sendBeacon、フォーム、ダウンロード、画像、スクリプト
- Aが止められなかったもの：新しいウィンドウ（window.open、target=_blank。別の接続先として開く。Fetch は、元のページにしか効かない）、WebSocket（Fetch の対象外）、Service Worker（別のターゲット）
- B・Cでも、新しいウィンドウは**開く**（`pages` が2以上）。ただし、中の通信は、遮断された
- WebSocket を、ホスト名で指定した外部へ向けた場合は、対照でも届かなかったため、この検証では判定できない（IP指定では、A＝届く、B・C＝遮断）

**結論と方針（提案。判断は、ルール管理者と仕様の責任者）**
- chrome-php/chrome の「エンジンによる検査（CDPのFetch）」**だけ**では、SEC-5・SEC-6を満たせない。仕様14-6の「不合格の場合の代替」に当たる
- 起動時の遮断（BまたはC）は、この15件を遮断できた。これを、**起動オプションで必ず付ける**（呼び出し側が外せない作りにする）。ただし、これは「Chrome自身の設定」であり、仕様SEC-6の「ネットワーク側（プロキシ、ファイアウォール）」の代わりにはならない。1bでは、OS・ネットワーク側の制限も、あわせて必要
- エンジン側の検査（A）は、**検知と停止**（SEC-5「新しいウィンドウ・タブが開いたら、停止」）のために併用する。新しいウィンドウは、`getPages()` の数や、`Target.targetCreated` で検知して、停止する。この検知は、まだ実装していない
- 別の部品（Node.jsのPlaywrightなど）に切り替える判断は、今回は、不要とみている（上の方針で、再検証して、合格すれば）
- 未検証：Chromeのバージョン差、Windows・Mac、実際の業務システム（SSOのリダイレクト、iframe、広告）、HTTPS（証明書エラー）、拡張機能・ポリシー、ダウンロードのダイアログ、プロキシの設定を、ページ側から変えられないこと

### 7-2. 使い捨てプロファイル（SEC-3、LOC-10）
- 既定で、一時ディレクトリが作られ、**正常終了のときは、消える**（確認済み）
- PHPのプロセスが SIGKILL されたとき：**ディレクトリも、Chromeのプロセスも、残る**（確認済み）。次の起動時に、残ったプロファイルを破棄し、Chromeを終了する処理が必要（14-3の5）。親が死ぬと、Chromeは親を失うので、緊急停止（子孫を探す）では見つからない。**ChromeのPIDも、開始時刻とともに、記録に残す**必要がある
- 未検証：パスワードの保存・拡張機能・テレメトリの無効化（chrome-php が付ける起動オプション：`--disable-sync`、`--disable-background-networking`、`--metrics-recording-only`、`--password-store=basic` など）が、実際に効いているか。chrome://policy で、会社のポリシーが強制する拡張機能が残らないか

### 7-3. デバッグ接続（仕様14-6）
- chrome-php は、`--remote-debugging-port=0` と `--remote-allow-origins=*` を、既定で付ける（TCPのポートを開く。パイプ方式 `--remote-debugging-pipe` には、対応しない）
- 待ち受けは、127.0.0.1（ループバックのみ）。Hostヘッダが IP でない要求は、拒否される（500。DNSリバインディングは、防げている）
- **既定では、どのWebページ（Origin）からの接続も、受け付ける**（Origin=http://evil.example で、101）。ユーザーの普段のブラウザで開いたページから、ポートを推測されて、操作されるおそれがある
- `customFlags` で、後から `--remote-allow-origins=http://127.0.0.1` を渡すと、既定の `*` を**上書きでき**、外部のOriginは 403 になる（確認済み）。**必ず、この指定を付ける**
- Originを持たない接続（同じPCの、別のプロセス）は、受け付ける。別のOSアカウントのプロセスからも、接続できる（ループバックのTCPのため）。chrome-php が、パイプ方式に対応しない限り、**防げない**。専用のOSアカウントでも、同じPCの別アカウントからは、接続できる。1bの条件（「他のOSアカウント・他のプロセスから使えないこと」）は、**この部品では満たせない**。代替：パイプ方式に対応した別の部品への切り替え（Playwright の `--remote-debugging-pipe` など）、または、ホストのファイアウォールで、ループバックの通信を、ユーザー単位で制限する（OSによる。未検証）

### 7-4. 対策の実装と、再検証（2026-11-11）
7-1〜7-3 の結果を受けて、次を実装し、本物のChromeで再検証した（Chrome for Testing 153.0.8010.12、PHP 8.3.6、Linux）。さらに、Opusのレビューで見つかった抜けも、直して、再検証した。

実装：
- `Src\Browser\ChromeLaunchPolicy`：許可した接続先（スキーム・ホスト・ポートの完全一致）だけから、起動オプションを作る（名前解決の失敗＋使えないプロキシ＋デバッグ接続のOrigin制限＋WebRTCの方針＋拡張機能などの無効化）。呼び出し側は、オプションを選べない
- `Src\Browser\ChromeBrowser`：上の方針で起動し、さらに、次を行う
  - エンジンが、CDPのFetchで、すべての要求を検査し、許可外の通信を失敗にして、記録する（検知して、停止するため）
  - 新しいウィンドウ・タブ、ダウンロード、想定外のダイアログ、主フレームが許可外へ移ること（about:blank・blob: を含む）を、検知して、停止（例外）にする。検知は、操作の前後（取り消せない操作の直前を含む）に確かめる
  - JavaScriptは、固定の文字列で、値は引数。さらに、ページのJavaScriptから隔離された環境（isolated world）で実行する（ページが querySelector などを差し替えても、読み取りが副作用にならない）
  - 使い捨てプロファイルの設定（Preferences）を、起動の前に書く：WebRTCのUDP禁止、パスワードの保存・自動入力・セーフブラウジングの無効化、ダウンロードの保存先をプロファイルの中にする
  - ダウンロードは、`Browser.setDownloadBehavior`（deny）で拒否し、検知する
  - 起動時に、Chromeのバージョンを記録し、許可したメジャーバージョンの外なら停止する（許可する範囲は、1bの前に決める。今は指定なし）
  - 取り消せない操作は、自分で持つ Guard で、証明を照合し直す
- 使い捨てプロファイルの記録：作成・破棄の通知（作ったワーカーのPIDと開始時刻つき）。異常終了のあとは、`nlrpa:recover`（と緊急停止）が、「--user-data-dir=ディレクトリ」と完全に一致するChromeと、そのディレクトリを回収する（置き場の外・形の違うディレクトリには、触らない。PIDと開始時刻が一致して、動いているワーカーのものは、触らない）

再検証の結果（`tests/Unit/ChromeBrowserTest.php`、`tests/Feature/WebTest.php`）：
- 15種類の攻撃を、外部をホスト名で指定した場合と、IPで指定した場合の両方で試し、**すべて、外へ届かなかった**（届いた要求は、case の付かないものも、すべて数えた）。このうち13種類は、エンジンが検知して停止にできた。WebSocket と Service Worker は、起動時の遮断が、黙って止めた（検知はしない）。対照（遮断なし）で、外部へ届くことも確認した。ホスト名で指定した外部では、名前解決の遮断が、そもそも名前を解決させないため、「届かない」ことの確認としては弱い。IP指定のほうが、強い確認になる
- **WebRTC（UDP）**：Opusのレビューで、外へ届くことが分かった（起動オプション `--force-webrtc-ip-handling-policy` だけでは、**効かなかった**）。プロファイルの設定（`webrtc.nonproxied_udp_enabled=false`）を、起動の前に書くと、届かなくなった（対照では届く）。**効くのは、設定の書き込み**
- **ダウンロード**：許可した接続先からでも、既定では、プロファイルの外（`~/Downloads`）に保存された。拒否して、検知するようにした。保存されないことを、確認した
- **ページによる関数の差し替え**：メインの世界で動く固定のJavaScriptは、ページに差し替えられ、`readValue` を呼ぶだけで、フォームが送信された。隔離された環境で実行するようにして、動かないことを確認した（対照では、罠が動く）
- **about:blank・blob:** への遷移：Fetch を通らないため、検知できなかった。主フレームの遷移（`Page.frameNavigated`）を検査して、検知するようにした
- 本物のChromeで、計画の承認 → ドライラン → 最終承認 → 登録 → 初回1件で停止 → 確認 → 残りの実行、が最後まで動いた。ドライランでは、取り消せない操作は、実行されなかった
- 使い捨てプロファイルは、作られ、終了時に消えた。親のPHPを SIGKILL して、孤児になったChromeと残ったプロファイルを、`nlrpa:recover` が回収した。動いているワーカーのものは、回収しなかった
- デバッグ接続は、外部のOriginが 403、chrome-php 自身のOriginだけが 101
- 起動オプションによる遮断の注意：`--proxy-server=http://127.0.0.1:1` は、「使えないプロキシ」として、接続が失敗することに頼っている。1番ポートで、何かが待ち受けていれば、通信が、そこへ流れる。検証では、何も待ち受けていない前提

### 7-5. 仕様14-6の合格基準に対する、現時点の状態
- 遷移の検査（SEC-5）：Linux・Chrome 153・15種類の攻撃＋追加の攻撃（WebRTC、ダウンロード、about:blank・blob:、関数の差し替え）では、**合格**。未検証の範囲は、下記
- 遷移以外の外部通信（SEC-6）：Chrome自身の設定による遮断は、上の範囲で合格。**OS・ネットワーク側の制限（プロキシ、ファイアウォール）は、未実施**（1bの条件）。UDPは、起動オプションでは止まらず、設定の書き込みで止まった。ほかのUDP・プロトコル（QUICなど）は、未検証
- 使い捨てプロファイル：正常終了・異常終了とも、合格（Linux）。拡張機能・テレメトリの無効化が、実際に効いているかは、未検証。パスワード保存は、設定で無効にしたが、効果は、未検証
- デバッグ接続：外部のOriginの制限は、合格。**同じPCの、他のプロセス・他のOSアカウントからの接続は、防げない**（ループバックのTCP。chrome-php が、パイプ方式に対応しないため）。1bの条件「他のOSアカウント・他のプロセスから使えないこと」は、**この部品では満たせない**。仕様14-6の「不合格の場合の代替」の判断（ルール管理者と仕様の責任者）が、必要
- 緊急停止：ワーカーと子孫の終了は、検証済み（偽のワーカーで）。Chromeを実際に動かしている最中の、緊急停止は、未検証
- 未検証：Chromeのバージョン差、Windows・Mac、IPv6（この環境にIPv6がない）、実際の業務システム（SSOのリダイレクト、広告のiframe）、HTTPS（証明書エラーを無視しないこと）、ファイル選択のダイアログ、プロキシ設定をページ側から変えられないこと（`chrome.proxy` のAPIは、ページにはなかった）、Chrome自身の通信の長時間の観察（約30秒では、見つからなかった）、ネットワーク側の制限との組み合わせ、`chrome://policy`
- 今の `nlrpa:worker` は、偽の部品（FakeBrowser）を使う。`ChromeBrowser` を、ワーカーへつなぐ設定（接続先の許可、画面の記録＝セレクタ、Chromeのパス）は、1bの作業として、残っている
