# 付録A 実行計画の形式（1a確定版）

仕様書の付録Aの骨子を、1aの実装用に確定したもの。検査は `src/Plan/PlanValidator.php`。

## 読み込み
- JSONは `Src\Plan\StrictJson` で読む（重複キー、2^53超の整数、不正なUTF-8を拒否）
- 知らない項目は、すべて拒否する

## 全体
| 項目 | 内容 |
|---|---|
| plan_id | `PLN-数字` |
| version | 1以上の整数 |
| plan_hash | 省略可。**信用しない**。実行エンジンが計算する値で上書きする |
| scenario_id | `SCN-数字` |
| created_by_ai | `{model, prompt_version}`（文字列） |
| allowlist_versions | `{operations, destinations}`（1以上の整数） |
| screen_record_version | 1以上の整数 |
| input.columns | 列定義の配列。**業務キー列（role=business_key）がちょうど1つ**（R8） |
| limits | `max_rows_per_run`（1以上）。`max_quantity_per_run` は任意。取り消せない手順があれば、`max_rows_per_run` は必須（R9） |
| unresolved | 「未確定」の一覧（文字列の配列、省略可）。1つでもあれば、実行できない（9-2） |
| steps | 手順の配列（1つ以上） |

## 列定義
`name`（重複不可）、`type`（text／number／date）、`required`（真偽）、`max_bytes`（任意）、`format`（任意）、`role`（任意。business_key／quantity／amount／personal_info）

## 手順
共通：`id`（`S-数字`。計画の中で重複不可）、`action`、`source`（シナリオの文。なければ null＝「AIが補った」）、`label`（表示用、任意）

- 操作（A-2）：`destination`（`{kind, name}`。**必須**。1aの kind は browser のみ、name は英数字・`_`・`.`・`-`）。open_url、read_text、type_text、clear_text、click、press_key、login、confirm_dialog、wait_for、write_result
  - `target`：画面の記録の要素名（open_url、read_text、type_text、clear_text、click、login で必須）
  - `value`（固定値）か `column`（入力データの列名）：type_text と write_result で、どちらか一方だけ。`column` は、列定義にある名前
  - `verify`：確認条件（**必須**）。`type` は text_visible／text_equals／element_exists／url_matches／value_matches。`value_matches` は `rule`（照合ルール）が必須
  - `timeout_sec`：wait_for で必須（上限は300）
  - `readback`：読み返し照合の項目の配列（任意。ただし、取り消せない手順に指定がなければ、12-1の関数が拒否する）。各項目は `target`（読み返す要素名）と、`column`（入力データの列）か `value`（固定値）のどちらか一方、`rule`（任意）
  - `reversible`：**信用しない**。AIが書いていても無視し、取り消し可否は `OperationPolicy` が計算する（R4）
- 構文（A-3）
  - `for_each_row`：`steps` を持つ。入れ子にできない
  - `if`：`condition`（確認条件）、`then`（手順の配列）、`else`（任意）
  - `on_dialog`：`dialog_text`、`response`（ok／stop）

## 照合ルール（rule）
`width`（full／half）、`date_format`（文字列）、`thousand_separator`（真偽）、`trim`（真偽）、`max_length`（整数）。すべて任意。

## AI出力の門（`AiPlanGate`）の決め事
- AIが書いた `plan_hash`、`reversible` は捨てる
- 必須の項目は、`null` を認めない（`source` だけ null 可。null は「AIが補った」の意味）
- 文字列は、制御文字（改行・タブを含む）、NUL、向きを変える文字（U+202Eなど）を拒否する
- 入力データの列（`column`）は、for_each_row の中でだけ使える
- 件数の上限は、読み取り・待ち・結果の記録以外が1つでもあれば必須（取り消し判定より広く取る）
- OKする確認ダイアログ（on_dialog の response=ok）は、取り消せない。同じ並びの click も、取り消せない扱い（7-1）
- 呼び出し側が渡せば、次も照合する：シナリオ（根拠の文）、人が定義した列、画面の記録の要素名、組織の件数の最大値

## 未確定（次に決める）
- press_key の「押すキー」の欄
- `created_by_ai`、`allowlist_versions`、`screen_record_version`、`plan_id` などの自己申告は、計画を作る処理（app側）が実行エンジンの値で上書きする。ゲートはまだ上書きしない
- `unresolved`（未確定）をAIが書かずに隠すことは、決定的な検査では防げない。承認画面で補う（方法は未定）

## 実行の登録（`RunRegistrar`）と、12-1の関数（`IrreversibleGuard`）で決めたこと
- 実行の前に、`RunRegistrar::register` で実行を登録する。ここで、最終承認、ドライラン、接続先、入力データ（R8）、件数・数量・金額の上限（R9）を検査し、「実行ID → 計画ハッシュ・ドライランID・接続先・各行の業務キーと値のハッシュ」を記録（ledger）に固定する
- 12-1の関数は、呼び出し側の自己申告を信じない。版・許可リスト・行の順番・件数・ドライランは、登録の記録から読む。行の値は、登録時のハッシュと照合する
- 計画は、関数の最初に深いコピーを取り、そのコピーだけを使う。許可オブジェクト（`Permit`）には、検査した時点の手順のコピーが入る
- 取り消せる手順は、この関数を通さない（取り消し可否は `OperationPolicy` が決める）
- `readback` がない取り消せない手順は、拒否する（安全側。必要なら、のちに緩める）
- 承認の記録は `{stage:'final', approver, os_user}`、ドライランの記録は `{dry_run_id, result, environment, destination_name}`。形が欠けた記録は無効。1aは environment=stub だけを有効とする。**承認の取り消し（revoke）は未実装**
- 拒否は、理由つきで ledger（kind=refusal）に記録する
- 「処理中」の保存が最後。「成功済みでない」「同じ業務キーに未解消がない」「停止の旗」の確認は、この保存と同じトランザクションの中で行う（同時実行の隙を作らない）。保存に失敗したら実行しない。実行後の異常・確認条件の不成立は、すべて「要確認」。実行後の状態の保存に失敗したら、「処理中」のまま残し（次の起動時に「要確認」になる）、呼び出し側には `executedButUnsaved` を返す
- 2行目以降は、`first_row_confirmed`（subject=実行ID）の記録があり、かつ1行目の同じ手順が「成功」のときだけ進める
- 許可オブジェクトの偽造対策（多重の防御）
  - `Permit` は複製・直列化を禁止し、Guardだけが知る使い捨ての合言葉（nonce）を持つ
  - 操作の部品は `GuardedAction` を継承する。`perform`（final）が `Guard::redeem` で、合言葉と保存先の状態（処理中、実行ID・計画ハッシュの一致）を照合し、使い捨ての証明（`Redeemed`）を返す
  - 本当に取り消せない操作をする瞬間は、`effect()` を通す。`effect()` は `Guard::assertRedeemed` で証明を照合し直してから、検査した時点の手順のコピーを渡す。継承して `execute` を直接呼ぶ裏口を作っても、`effect` を通らなければ操作できない（ブラウザの部品は、操作の瞬間に必ず `effect` を使うこと）
  - リフレクションでコンストラクタを直接呼んで偽造しても、合言葉・token を知らないので、止まる（テストで確認）
  - アーキテクチャのテストで、`IrreversibleAction` の実装は `GuardedAction` の継承に限ること、`src/` でリフレクションによる生成をしないことを確かめる
- 取り消し可否は、承認済みの個別登録（計画ハッシュに含まれる `hashInputs['registrations']`）から、Guardの中で計算する。形：`{buttons, autosave_free_inputs, urls, password_fields}`。それぞれ `[{destination, target}]`
- 業務キー：NFKC正規化で変わらない、空白・制御・書式文字を含まない、200バイト以内。大文字小文字は**区別する**（`K-001` と `k-001` は別。利用者に確認済み）。保存・比較の入り口は `BusinessKey::fold`（今は、そのまま返す）
- 入力データの検査（R8）：型（number／date。date の format は YYYY-MM-DD 形式）、必須、max_bytes、制御文字、業務キーの重複。数量・金額は、負の値・不正な形を拒否し、小数4桁の固定小数で合計する（浮動小数点の丸めで上限を超えさせない）
- 「初回1件」の確認の記録には、確認者（`by`、`os_user`）が必要。その1件の「成功」より後に記録されたものだけが有効
- 実行後に状態を保存できなかったときは、kind=`post_exec_failure` で記録する（拒否と区別する）
- 状態の表（step_states）が、記録（ledger）の最新と食い違っていれば、拒否する。表と旗の削除は、トリガーで拒否する。旗は、表が0でも、記録の最新が「立っている」なら、立っているものとして扱う

## 既知の限界・未実装（Opusレビューで挙がったもの）
- ledger は、末尾の記録をまとめて消されても、`verify()` では見つからない（先頭のハッシュの外部への退避がないため）。鍵もないため、全体を計算し直されれば、改ざんは見つからない。「部分的な改ざんのみ検知できる（未検証）」以上のことは言わない（LOC-8）
- `ledger->append()` は、同じプロセスから誰でも呼べる。承認・ドライラン・実行の登録（run）・初回確認・旗（flag）の記録を、偽って追記できる。とくに、`run` を偽れば、数量・金額の上限を迂回できる（Guardは件数の上限だけ、計画と照合し直す）。承認画面・ワーカーの分離と、別のOSアカウントは、1bの条件
- 同じ業務キーの別の手順の「未解消」の確認（`unresolvedFor`）は、状態の表だけを見ている。ledger との突き合わせは、実行する手順だけ
- 実行の登録に、SEC-13の項目（実行者、実行PC、入力ファイルのハッシュ）が、まだない
- `IrreversibleGuard` は、組織全体の件数の最大値（SEC-14）を見ない。登録時（`RunRegistrar` の `orgMaxRows`）だけ
- `recoverAfterCrash` は、実行中のワーカーがいても呼べてしまう。14-3の6のファイルロックは、Runner で実装する
- 接続先は、名前でしか照合していない。スキーム・ホスト・ポートと種類の照合は、ブラウザの部品（1b）で行う
- 計画ハッシュの照合は、この関数では「直前」の1回だけ。ドライランの開始時・実行の開始時の2回は、Runner で行う
- 「初回」は、今は実行（run_id）ごと。版ごとの最初の1回にするかは、仕様から判断できないので、要確認

## SQLiteについて（仕様14-3の「要確認」の結果）
- PHP 8.3.6 の pdo_sqlite では、`exec('BEGIN IMMEDIATE')` で始めたトランザクションを、`PDO::inTransaction()` は認識しない（`false` を返す）。そのため、`Db::immediate` は `inTransaction()` に頼らず、自分で管理している深さで COMMIT / ROLLBACK する
- PHP 8.5.12 で同じ挙動かは、未確認（8.5.12 が用意できたら確認する）

## 実行PCで必要なPHP拡張（実装で判明）
- `intl`（業務キーのNFKC正規化）、`mbstring`、`pdo_sqlite`。TECH_STACK.md の更新対象

## 確認条件（verify）の意味（Runnerで確定）
- `text_visible`：画面に、`value` の文字がある
- `text_equals`：`target` の値が、`value`（固定値）と等しい
- `element_exists`：`value` という名前の要素が、画面にある
- `url_matches`：開いている画面の名前が、`value` と等しい
- `value_matches`：`target` の値が、入力データの列（`value` は**列名**）の値と、`rule` のもとで一致する
- 知らない種類は、不合格

## Runner（`PlanRunner`）で決めたこと
- ドライラン：計画の承認（stage=plan または final）が必要。取り消せない操作の手前で、読み返し照合だけ確かめて、その行を終え、各行の終わりに画面を初期状態へ戻す。結果は ledger の `dry_run`（environment=stub、接続先、合否）に記録する。状態（step_states）は変えない
- 本番：実行の登録（`RunRegistrar`）が済んでいること。計画ハッシュ・入力データの並び（登録した順番）を確かめる。取り消せない手順は、Guard（12-1）だけが通す
- 初回は1件だけ実行して止まる（`awaiting_first_row_confirmation`）。人が `confirmFirstRow` で確認を記録してから、残りを実行する
  - 「初回の1件」は、**その実行（run_id）で、最初に実際に実行した行**。前の実行で成功した行は、数えない。行の中の取り消せない手順は、複数あってよい（条件分岐で、通らない手順があってもよい）。「実行した」とは、その行で、どれか1つでも、この実行で手を付けたこと（`FirstRowGate`）。取り消せない手順を何も実行しなかった行は、初回の1件に数えない
  - 確認の記録は、対象の業務キー・確認者・OSユーザー・ホスト名を持つ。有効なのは、その行がこの実行で手を付けた手順が、すべて「成功」で、確認がその成功より後に記録されたものだけ（人が「要確認」を判定した場合は、判定のあとに、あらためて確認する）
  - 同じ計画の、ほかの実行が「初回の1件を実行して、確認待ち」なら、新しい実行は、開始できない（Runner の開始時と Guard の両方）。登録し直して、確認なしに1行ずつ進めることはできない
- すでに成功した行は、飛ばす（別の実行ID・別の版でも）
- 二重起動は、ファイルロック（`RunLock`）で防ぐ。取れなければ、開始しない
- 各手順の前に、キルスイッチ・停止の旗を読む。想定外の確認ダイアログが開いていたら停止する
- 取り消せない操作の瞬間は、`BrowserPort::performIrreversible` が、証明（Redeemed）を Guard で照合し直してから行う。対象の要素は、検査した時点の手順から取る（呼び出し側は指定できない）
- 1aの未対応：`on_dialog` の自動対応（出たら停止）、`login`、`press_key`、`confirm_dialog`、`wait_for` の待ち（1回判定するだけ）、`write_result`（判定のみ）
- 取り消し可否の登録（`hashInputs['registrations']`）の例：スタブ画面では、入力欄 `item_code`・`quantity` を「自動保存なし」、`login_page`・`order_page` をURLとして登録し、`submit_button` は登録しない（＝取り消せない）

## Runnerのレビューで直したこと／残した限界
直したこと：
- すべての手順の接続先が、実際の接続先と一致しなければ開始しない（登録は接続先ごと。7-1-1）
- ブラウザ部品は、自分で持つ Guard で証明を照合する（引数で渡された Guard は信用しない）。`FakeBrowser` のコンストラクタで結び付ける
- 本番の開始時に、最終承認・合格したドライラン・接続先を確かめる（取り消せる手順が実行されてから、Guardに止められるのを防ぐ）
- 取り消せる手順が使う行の値も、実行の前に、登録時のハッシュと照合する。件数が登録と違えば、開始しない
- 画面を初期状態へ戻せなければ、停止する（ドライランも不合格）
- ドライランの記録の environment は、ブラウザ部品から取る（`environmentName()`）。部品を差し替えたら、別の環境として記録される
- 本番の開始時（ロックを取ったあと）に、`recoverAfterCrash` を呼ぶ（14-3の5）
- 1aの制約として、次を含む計画は、開始しない：OKする確認ダイアログ（on_dialog）、for_each_row の外の取り消せない手順
- 取り消せない手順に読み返し照合の項目がなければ、ドライランで不合格にする

残した限界（1bまでに対応）：
- ポートの取り消せるメソッド（typeText、openUrl、clearText、resetToStart）は、登録を見ない。取り消し可否の判定は Runner にだけある。chrome-php 版では、ポートにも、承認済みの登録（`OperationPolicy`）を持たせて、登録外の対象を拒否する（多重の防御）。`resetToStart` の手段も、接続先の定義（7章）で登録したものに限る
- URL・ホストの照合（SEC-5）、要素の特徴の照合（7-1-1）、自動保存の有無、確認ダイアログ、待ち時間の上限（R20）は、偽の部品にない
- `FakeBrowser` の試験用の仕掛け（`typedValueTransform` など）は、public のプロパティ。本番用の部品には持たせない
- ロックファイルの場所は、呼び出し側が渡す（設定で変えられないようにするのは、app 側で行う）。14-3の6の「保存先の一意制約」は、Runner の側にない（Guard が、保存先で「処理中」の二重を防いでいる）
- 緊急停止（プロセスIDのワーカーとChromeをまとめて終了する専用コマンド）は、未実装（app/Console で作る）

## 画面・コマンド（app/）で決めたこと
- 待ち受けは 127.0.0.1 だけ。起動コマンド（`nlrpa:serve`）が `php -S` を直接起動し、`-d` で PHP の設定を渡す（Laravelの `artisan serve` は、子のプロセスに `-d` や環境変数を引き継がないため）。ポートが使用中なら、トークンを発行しない
- Hostヘッダ（localhost・127.0.0.1・[::1] と設定したポート）、POST以外の拒否、Origin（ポートまで完全一致・必須）、CSRF、CSP（インラインのJS・スタイルなし）、`frame-ancestors 'none'`、`no-store`、CORSなし。アクセストークンは、セッションにハッシュを持ち、毎回、保存済みのハッシュと `hash_equals`
- 画面は、実行要求を記録するだけ。ワーカーは、担当者がコンソールで、要求の番号だけを指定して起動する（画面からプロセスを起動しない。テストで確認）
- 承認者・確認者の名前は、画面で入力する（自己申告）。OSのユーザー名・ホスト名と一緒に、記録（ledger）に残す。作成者と同じ人が承認したかも、記録に残す。「要確認」の判定者は、「名前（OSユーザー）」を状態の記録の `by` に残す（ホスト名はない）
- 計画と一緒に、許可リスト・個別登録・画面の記録の中身を保存し、保存した内容から計画ハッシュを計算し直して照合する。今の内容（`StubRegistrations`）と違う古い計画は、承認・ドライラン・登録・実行ができない（再承認が必要）
- 取り込んだ入力データは、ハッシュを保存し、使うたびに照合する
- 1aの許可リスト・個別登録は、`StubRegistrations` の固定の内容。ルール管理者の管理画面（R22）はない
- 緊急停止：キルスイッチを立て、記録したワーカーと子孫のプロセスを終了する（Linuxの `/proc` のみ）。ワーカーは、起動時に、PIDと開始時刻（`/proc` の starttime）を記録する。**PIDと開始時刻が一致するプロセスだけ**が対象（PIDが再利用された別のプロセスは、終了しない。コマンドラインの書き方には、頼らない）。終了の手順は、全体に SIGSTOP を送って止め、子孫を数え直して、安定してから SIGKILL。終了できなければ、失敗として報告し、登録は残す
- 起動コマンドは、親が SIGINT・SIGTERM・SIGHUP を受けたら、子のサーバーにも終了を伝える。ポートが1〜65535の整数でなければ、トークンを発行しない
- データの置き場が、リポジトリの中かは、「//」「..」やシンボリックリンクを整理してから判定する（`Engine::resolvePath`）。作る前に判定する

## 残した限界（画面・コマンド）
- プレビューで見せたハッシュを、登録のときに照合していない（登録は、プレビューを飛ばして、直接できる）。入力データのハッシュは、登録の記録（ledger）に残る
- 計画ハッシュが同じ計画は、最初の作成者とシナリオが残る（同じ内容を、別の人が作っても、新しい行にならない）
- `nlrpa:recover` と、ワーカーの起動直後（ロックを取る前の短い間）が重なると、その要求が「異常終了」と記録されることがある（実行の結果で、上書きされる）
- セッションのクッキーは、ポートで分かれない（localhost の別ポートのページが、クッキーを上書き・削除できる。ログアウトさせられる程度）
- CSVの値・列名・シナリオの表示に、向きを変える文字・ゼロ幅の文字が入りうる（登録対象の列は、登録のときに拒否する）。表示の偽装は、防いでいない
- 仕様のうち、1aで未実装：計画の差分表示（R3）、業務キー列を画面で指定すること（5章の3。今は計画の列定義の role）、手順ごとの確認条件の合否の表示（5章の7）、承認画面の「本番の別の人の承認」（第2段階）
- 緊急停止は、Linux以外では、キルスイッチを立てるだけ（11章：OSは未確認）
- 1行に取り消せない手順が複数あり、途中の手順を「未実行」と判定した行は、自動では再開しない。画面は初期状態に戻っているため、すでに成功した手順（例：入力）を飛ばすと、次の手順の読み返しが合わなくなる。二重には実行せず、止まる。再実行するには、業務キーを変えて（枝番を付けて）、承認者が理由を記録する（9-4）
- 親のコマンドを SIGKILL で止めたときは、子のサーバーが残る（終了を伝えられない）。ポートが使用中になるので、次の起動で、気付ける
- 空きを確かめてから、実際に待ち受けるまでの間に、別のプロセスがポートを取りうる（その場合、トークンは発行済みになる）
- 緊急停止は、ブラウザの待ちの間も効くが、SQLite が busy のときの動きは、確かめていない

## 本物のChromeを、ワーカーにつなぐ（1b）で決めたこと
- ブラウザ部品は、設定（`NL_RPA_BROWSER`）で、`fake`（偽の部品）か `chrome`（本物。`ChromeBrowser`）を選ぶ。許可する接続先は、スタブの画面（Web版。`NL_RPA_STUB_PORT`）の1つだけ。アプリ自身のポート（8080）は、許可できない（14-4）
- 画面の記録（画面名とパス、要素名とセレクタ）は、`StubRegistrations`（計画ハッシュの入力 `screen_record` の中身）。接続先（スキーム・ホスト・ポート）は、設定で決め、計画ハッシュには、パスだけが入る
- ドライランの環境は、ブラウザ部品が決める（`fake`＝stub、`chrome`＝chrome）。有効と認める環境は、今のモードの1つだけ。切り替えると、もう一方のドライランは、無効（9-2）
- ワーカーは、終了時に、ブラウザを必ず閉じる（使い捨てプロファイルの破棄）。閉じる時点の、Chromeのバージョンと、確かめていなかった異常（最後の操作のあとに起きたもの）を、ledger（worker の finished）に残す
- `nlrpa:stub-web`：スタブの発注画面を、127.0.0.1の別ポートで起動する。発注の登録は、データの置き場の `stub-orders.log` に残り、実行の画面に出る
- 許可するChromeのメジャーバージョンは、設定（`NL_RPA_CHROME_MAJOR`）。未指定なら、確認しない。範囲は、1bの前に、TECH_STACK.md に決める（仕様11章）
- 複数のプロセスが、同時に、新しいデータベースを開くと、「database is locked」で失敗した。作成・設定の切り替え・表の作成を、ロック中は、短い間隔で繰り返すようにした（回帰テストあり）
